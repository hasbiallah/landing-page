## Problem Statement

PRD v2.0 (Vercel-only) approach memiliki kelemahan:
1. **Tidak scalable** — setiap customer butuh setup deployment terpisah (Railway/Render account, Git repo, dll)
2. **Support burden tinggi** — hasbi.dev harus guide setup per customer
3. **No recurring revenue** — one-time payment, tidak ada MRR (Monthly Recurring Revenue)
4. **Hard to iterate** — kalau ada bug fix atau fitur baru, harus update repo semua customer

## New Approach: Multi-Tenant SaaS Platform

**Konsep**: Satu aplikasi WhatsApp Bot yang bisa handle **multiple tenants/customers** dalam satu codebase.

**Arsitektur**:
- **Backend**: Node.js + Express API untuk manage tenants, bots, keywords
- **WhatsApp Engine**: Baileys (1 instance per tenant, managed by backend)
- **Database**: PostgreSQL (multi-tenant schema: `tenants`, `bots`, `keywords`, `messages`)
- **Frontend Dashboard**: Astro + Tailwind (untuk customer manage bot mereka sendiri)
- **Deployment**: localhost dulu (dev), nanti Vercel (frontend) + Railway (backend+DB)

**Customer flow**:
1. Customer beli paket → hasbi.dev bikin tenant account
2. Customer login ke dashboard (`dashboard.hasbi.dev`)
3. Customer scan QR code untuk connect WA mereka
4. Customer manage keywords, reply messages, broadcast via dashboard
5. Bot jalan 24/7 di backend hasbi.dev (customer tidak perlu deploy sendiri)

**Monetization**:
- **Paket Hemat (Rp299rb)**: one-time setup + Rp50rb/bulan hosting fee (recurring revenue!)
- **Paket FYP (Rp990rb)**: one-time setup + Rp100rb/bulan hosting fee + landing page
- **Paket Cuan (Rp2.5jt)**: one-time setup + Rp200rb/bulan hosting fee + premium features

### Tech Stack

**Backend**:
- **Runtime**: Node.js 20+
- **Framework**: Express.js (REST API)
- **WhatsApp**: Baileys v6+ (multi-session support)
- **Database**: PostgreSQL 15+ (via Railway/Neon.tech)
- **ORM**: Prisma (type-safe, migration-friendly)
- **Auth**: JWT (JSON Web Token) untuk customer login
- **Storage**: PostgreSQL BYTEA untuk session data (atau Redis untuk production scale)

**Frontend Dashboard**:
- **Framework**: Astro v4 (SSR mode, bukan static)
- **Styling**: Tailwind CSS
- **UI Components**: Headless UI (accessible components)
- **State Management**: Nano Stores (lightweight)
- **HTTP Client**: Fetch API (native)

**DevOps**:
- **Localhost**: Docker Compose (backend + PostgreSQL + frontend dev server)
- **Production**: Railway (backend + PostgreSQL), Vercel (frontend SSR)
- **Monitoring**: Sentry (error tracking), Uptime Robot (health check)

## Database Schema (Multi-Tenant)

### PostgreSQL Tables

```sql
-- Tenants (customers)
CREATE TABLE tenants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(255) NOT NULL,
  email VARCHAR(255) UNIQUE NOT NULL,
  phone VARCHAR(20) UNIQUE NOT NULL,  -- nomor WA customer
  package_type VARCHAR(20) NOT NULL,  -- 'hemat', 'fyp', 'cuan'
  status VARCHAR(20) DEFAULT 'active', -- 'active', 'suspended', 'cancelled'
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Bot instances (1 per tenant)
CREATE TABLE bots (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  whatsapp_phone VARCHAR(20) NOT NULL,  -- nomor WA yang dipakai bot
  status VARCHAR(20) DEFAULT 'disconnected', -- 'connected', 'disconnected', 'pairing'
  qr_code TEXT,  -- QR code base64 untuk pairing (temporary)
  session_data BYTEA,  -- Baileys session data (encrypted)
  last_connected_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  UNIQUE(tenant_id)
);

-- Keywords (auto-reply rules)
CREATE TABLE keywords (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  trigger_words TEXT[] NOT NULL,  -- array of keywords (case-insensitive)
  reply_message TEXT NOT NULL,
  is_active BOOLEAN DEFAULT TRUE,
  priority INT DEFAULT 0,  -- untuk handle multiple match (highest priority wins)
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Message history (incoming & outgoing)
CREATE TABLE messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  bot_id UUID REFERENCES bots(id) ON DELETE CASCADE,
  direction VARCHAR(10) NOT NULL,  -- 'incoming' or 'outgoing'
  from_number VARCHAR(20) NOT NULL,
  to_number VARCHAR(20) NOT NULL,
  message_body TEXT,
  matched_keyword_id UUID REFERENCES keywords(id),  -- null if no match
  created_at TIMESTAMP DEFAULT NOW()
);

-- Broadcast campaigns (Cuan only)
CREATE TABLE broadcasts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  message TEXT NOT NULL,
  target_numbers TEXT[],  -- array of phone numbers
  status VARCHAR(20) DEFAULT 'pending',  -- 'pending', 'sending', 'completed', 'failed'
  sent_count INT DEFAULT 0,
  failed_count INT DEFAULT 0,
  created_at TIMESTAMP DEFAULT NOW(),
  completed_at TIMESTAMP
);

-- Landing pages (FYP & Cuan only)
CREATE TABLE landing_pages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  slug VARCHAR(100) UNIQUE NOT NULL,  -- subdomain atau path: /p/toko-sayaaa
  config JSONB NOT NULL,  -- site-config.yml as JSON
  is_published BOOLEAN DEFAULT FALSE,
  custom_domain VARCHAR(255),  -- optional custom domain
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Indexes for performance
CREATE INDEX idx_tenants_email ON tenants(email);
CREATE INDEX idx_bots_tenant_id ON bots(tenant_id);
CREATE INDEX idx_keywords_tenant_id ON keywords(tenant_id);
CREATE INDEX idx_messages_tenant_id ON messages(tenant_id);
CREATE INDEX idx_messages_created_at ON messages(created_at DESC);
CREATE INDEX idx_broadcasts_tenant_id ON broadcasts(tenant_id);
CREATE INDEX idx_landing_pages_slug ON landing_pages(slug);
```

### Session Persistence

Baileys session disimpan di PostgreSQL `bots.session_data` (BYTEA column, encrypted).

**Flow**:
1. Customer scan QR code → Baileys generate `creds.json` + `keys.json`
2. Backend encrypt session data, save ke DB
3. Kalau backend restart, load session dari DB → Baileys reconnect otomatis (no rescan QR)


### Enforcement in Code

```javascript
// backend/src/middleware/packageLimits.js

async function checkKeywordLimit(req, res, next) {
  const tenant = await getTenant(req.tenantId);
  const keywordCount = await countKeywords(req.tenantId);
  
  const limits = {
    hemat: 5,
    fyp: 20,
    cuan: Infinity
  };
  
  if (keywordCount >= limits[tenant.package_type]) {
    return res.status(403).json({
      error: 'Keyword limit reached',
      limit: limits[tenant.package_type],
      current: keywordCount,
      upgrade_url: '/upgrade'
    });
  }
  
  next();
}
```

| **WhatsApp ban (unofficial API)** | 🔴 High — customer bot offline | Dokumentasi: gunakan nomor baru, migration path ke WA Business API |

## Further Notes

- **Multi-tenant isolation critical** — semua query harus filter by `tenant_id`, test with 2+ tenants sebelum production
- **Session encryption wajib** — Baileys session berisi credentials, encrypt before save to DB
- **Rate limiting** — protect API dari abuse (express-rate-limit)
- **Monitoring** — Sentry for backend errors, Uptime Robot for health check
- **Backup** — Railway PostgreSQL auto-backup daily, tapi setup manual backup script weekly ke S3/GCS
